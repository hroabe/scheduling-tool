# 機能追加仕様：通常イベント（日程調整）ブラッシュアップ＋機能盛り込み v1
対象：1on1ではない「みんなの予定を調整する」イベント
前提：Next.js(App Router) + Chakra UI / 既存機能は維持 / UI統一済み前提で機能を追加

---

## 0. 目的（今回の追加分）
1) 候補日ごとの回答状況（候補日一覧 + 進捗/○数/おすすめ表示）を実装する  
   - 添付イメージの「左下」のようなUI（候補日ごとのバー/件数）  
2) 予定の確定機能（主催者が候補日を確定し、イベント状態を「確定」にする）を実装する  
   - 確定後の表示、回答可否、CSV/共有、締切の扱いも整備する

---

## 1. 用語・ステータス
- EventStatus: `OPEN | CLOSED | FIXED`
  - OPEN: 回答受付中
  - CLOSED: 回答締切（確定前で締切）
  - FIXED: 予定確定（確定後）
- CandidateSlot: 候補日時（例：1/7 10:00-11:00）
- Response: 参加者回答（候補ごとに ○/△/×）
- FinalDecision: 主催者が確定した候補（CandidateSlotへの参照）

---

## 2. 画面/タブの機能追加（共通）
Event Detail（回答状況 / 回答する / 集計結果）

### 2-1. 共通ヘッダーに「確定」状態の表現を追加
- タイトル横のステータスBadge
  - OPEN: 「回答受付中」
  - CLOSED: 「回答締切」
  - FIXED: 「確定」
- FIXED のときヘッダー直下に「確定日時」表示（強調）
  - 例：`確定：1/8（木）10:00 - 11:00`

### 2-2. 「回答する」タブの扱い（ステータス別）
- OPEN: 通常通り回答可能
- CLOSED: 回答フォームを無効化し、案内文表示
  - 文言例：`このイベントは回答締切となりました。主催者の確定をお待ちください。`
- FIXED: 回答フォームを非表示（または無効化）し、確定日時を表示
  - 文言例：`予定が確定しました。上記の日時で実施します。`

## 3. 機能①：候補日ごとの回答状況（Candidate Summary）
### 3-1. どこに表示するか
- 「集計結果」タブに必須（推奨：画像のように “候補日一覧＋おすすめカード” を同一セクションに）
- 「回答状況」タブにも簡易表示を追加してよい（候補切替ナビとして使える）

### 3-2. UI要件（Desktop）
集計結果タブ内に「候補日ごとの回答状況」セクションを追加：

- 左：候補日一覧（CandidateSummaryList）
  - 行要素（CandidateRow）：
    - 日付（例：1/7（水））＋時間（10:00-11:00）
    - 横バー（進捗）※長方形・直線
      - 進捗は「○」割合、または「○+△」割合（要件で選択）
    - 右側に `○件数` を小バッジ表示（例：○2）
    - 行クリックで右の詳細カードを切り替える
  - 並び順：
    1. おすすめ（スコア最大）を先頭にピン留め可
    2. それ以外は日時順

- 右：おすすめ/詳細カード（CandidateDetailCard）
  - 選択中候補の
    - 日付＋時間（大きめ）
    - `おすすめ` バッジ（おすすめ候補のみ）
    - `回答数/参加者数`（例：2/2名）
    - 内訳チップ：○/△/× の件数
    - （任意）積み上げバー（○/△/×）

### 3-3. UI要件（Mobile）
- 候補日一覧を縦積み（カードまたはリスト）
- 右側詳細カードは下に表示 or モーダル（実装しやすい方でOK）
- 横幅で崩れないこと（表現を簡略化してOK）
  - 例：候補行：日時 + バー + ○件数

### 3-4. 計算仕様（おすすめ候補のスコア）
- score = 3 * count(○) + 1 * count(△) - 2 * count(×)
- tie-breaker:
  1) count(○)が多い
  2) count(×)が少ない
  3) 日時が早い
- 参加者数は「回答済み人数」ではなく「回答者数」をベースにするか選べる
  - 推奨：カードには `回答者数/招待人数` として表示
  - 招待人数がない場合は `回答者数` のみ

### 3-5. 受け入れ条件
- 候補日が複数ある場合、一覧が必ず表示される
- クリック/タップで右（または下）の詳細が切り替わる
- 進捗バーは楕円ではなく長方形（角丸2px程度）
- おすすめ候補が必ず1つ付与される（候補が1つならそれがおすすめ）

## 4. 機能②：予定の確定（主催者が確定する）
### 4-1. どこから確定するか（導線）
- 「集計結果」タブに Primary ボタン `この候補で確定` を配置
  - CandidateDetailCard 内（おすすめ候補表示の近く）に置くのが最短導線
- 主催者のみ操作可能（権限要件は後述）

### 4-2. 確定フロー（UI）
1) 主催者が候補を選択（CandidateDetailCardで表示中の候補）
2) `この候補で確定` を押す
3) 確認モーダル
   - タイトル：`この日時で確定しますか？`
   - 表示：日時、参加者回答内訳（○△×）
   - オプション（任意）：
     - `イベントを回答締切にする（確定と同時に）` → 既定ON
     - `参加者へ確定通知を送る`（メール等がない場合は「共有リンクを再送」でも可）
4) 実行後
   - EventStatus を FIXED に
   - header に確定日時を表示
   - 回答フォームは無効化（FIXED仕様）
   - 一覧のカードにも「確定」バッジ＋確定日時サマリ表示

### 4-3. 確定後の振る舞い
- EventStatus=FIXED
  - 参加者向けページの最上部に「確定日時」カードを表示
  - `回答する` は無効（または閲覧のみ）
  - `集計結果` は閲覧可能（主催者はCSV可能）
- 再オープン（任意）
  - 主催者に `確定を取り消す`（danger/confirm）を提供するかは要件で決める
  - v1では「取り消し不可」でもOK（要件に明記）

### 4-4. 締切機能（CLOSED）
- 主催者が `回答を締め切る` を押すと EventStatus=CLOSED
- CLOSED の時
  - 回答入力は不可
  - 集計・確定は可能
- FIXED と CLOSED は別
  - FIXED は確定日時が入っている状態
  - CLOSED は確定前の締切状態

### 4-5. 権限（ログインなし運用の場合）
- 主催者操作（締切/確定/編集）は「編集キー」方式を採用（推奨）
  - event作成時に `admin_edit_key` を生成し、URLに含める or 別途保存
  - サーバには平文保存しない（ハッシュ化して保存）
- 参加者は通常URL（閲覧/回答のみ）でアクセス可能

### 4-6. データ仕様（最小追加）
Event:
- status: OPEN|CLOSED|FIXED
- fixed_candidate_id?: CandidateSlot.id
- fixed_at?: datetime
- closed_at?: datetime
- admin_edit_key_hash: string（既存にあるなら利用）

CandidateSlot:
- id, start_at, end_at, label（日付表示用）

### 4-7. API仕様（例）
- POST `/api/events/{eventId}/close`
  - auth: admin_edit_key
  - result: status=CLOSED
- POST `/api/events/{eventId}/fix`
  - body: { candidateId: string }
  - auth: admin_edit_key
  - result: status=FIXED, fixed_candidate_id=candidateId, fixed_at=now
- POST `/api/events/{eventId}/unfix`（任意）
- GET `/api/events/{eventId}/summary`
  - 各候補の counts: { circle, triangle, cross, totalResponders }

※既存APIがあるなら、その構造に合わせて「追加フィールド/追加エンドポイント」を最小化すること

### 4-8. 受け入れ条件
- 主催者が候補を選んで確定できる
- 確定後、イベント状態が FIXED になり、表示が切り替わる
- 一覧カードに「確定」表示と確定日時が出る
- 回答ページは確定後に回答不可になる
- API/DB変更は最小で、既存イベントにも影響がない（migration安全）

- FIXED/CLOSED/OPENで「回答する」タブの挙動が変わる
- Mobileで崩れない（バーやボタンのはみ出しなし）
